# GitHub runners (`pipelines.github.runner`)

Every job catladder generates for GitHub Actions runs on github's hosted
`ubuntu-latest` (2 vCPU / 8 GB for private repos, $0.006/min) unless
`pipelines.github.runner` says otherwise. Because catladder runs each
job in its own `container:` image and uses `actions/cache`, the runner
machine is interchangeable: third-party runner providers that plug into
GitHub Actions work without other changes.

Golden rule: never edit `runs-on` in `.github/workflows/catladder-*.yml`
— set it in `catladder.ts` and regenerate (`catenv`).

## Configuration

```ts
pipelines: {
  github: {
    // shorthand: one runner for all component jobs
    runner: { provider: "blacksmith" },
  },
},
```

```ts
pipelines: {
  github: {
    runner: {
      // component/workspace jobs: build, test, lint, docker, deploy, …
      default: { provider: "celesto", size: "memory" },
      // per job (name without emoji), optionally "<component>/<job>"
      jobs: { test: { provider: "celesto", size: "large" } },
      // per environment — wins over `jobs` and `default`
      environments: { prod: "ubuntu-latest" },
      // catladder's housekeeping jobs (image check, ✅ aggregate checks,
      // review deploy triggers/guards, changeset check)
      light: { provider: "celesto", size: "standard" },
      // the release jobs (create release, release on green) — default: light
      release: "ubuntu-latest",
    },
  },
},
```

| runner value                        | `runs-on` label                                                                                    |
| ----------------------------------- | -------------------------------------------------------------------------------------------------- |
| any string                          | used as is (`ubuntu-latest`, a larger github runner, a self-hosted label)                          |
| `{ provider: "blacksmith", vcpu? }` | `blacksmith-<vcpu>vcpu-ubuntu-2404`, vcpu 2 (default) / 4 / 8 / 16 / 32                            |
| `{ provider: "celesto", size? }`    | `celesto-<size>`: micro 1/2 GB, small 1/4, standard 2/4, memory 2/8 (default), large 4/16, xl 8/32 |

Resolution for a component job: `environments[env]` → `jobs["<component>/<job>"]`
→ `jobs["<job>"]` → `default` → `ubuntu-latest`. Job keys are the job
name without emoji, lowercased: `app`, `test`, `lint`, `audit`,
`docker`, `deploy`, `verify`, `stop`, … (`🧪 test` → `test`).
`light` defaults to the provider's small size (blacksmith 2 vCPU,
celesto `standard`) or to `default` when that is a literal label.
`release` defaults to `light`. Housekeeping and release jobs ignore
`environments` and `jobs`; set `release` explicitly to keep the release
jobs (they push with the release deploy key and publish) on github's
runners.

Housekeeping jobs run for seconds, but github bills every job as at
least one full minute, so a busy repository pays for hundreds of these
"minutes" a day. Moving `light` to a provider's smallest size (celesto
`micro`, blacksmith 2 vCPU) removes most of the remaining github bill;
the price is the provider's pickup time (10–50 s on celesto) on every
step of the review deploy chain.

Only x64 Ubuntu runners are offered as providers: catladder's job
images are built x64-only. Use a literal label for anything else.

## 1. Measure before deciding

Most projects use 1–3k minutes a month — inside the org's included
minutes, so switching saves little. It pays off for projects with many
pushes (agents pushing to PRs, many review deploys) or slow test jobs.

Monthly Actions usage per repository (needs an org admin's token):

```sh
gh api "organizations/<org>/settings/billing/usage?year=2026&month=11" \
  --jq '[.usageItems[]|select(.product=="actions" and .sku=="Actions Linux")]
        | group_by(.repositoryName)
        | map({repo: .[0].repositoryName, minutes: (map(.quantity)|add|round)})
        | sort_by(-.minutes)'
```

Which jobs dominate: sum the durations of the jobs of a day's runs
(`gh api repos/<owner>/<repo>/actions/runs?created=<date>` then
`.../runs/<id>/jobs`). GitHub bills every job rounded up to a full
minute, so many tiny jobs cost more than their runtime suggests.

## 2. Estimate

List prices (checked November 2026 — verify on the providers' pages
before quoting them):

|                        | per minute (2 vCPU / 8 GB) | free                        | notes                                                                                 |
| ---------------------- | -------------------------- | --------------------------- | ------------------------------------------------------------------------------------- |
| github `ubuntu-latest` | $0.006                     | org plan's included minutes |                                                                                       |
| Blacksmith             | $0.004 (scales with vCPU)  | 3,000 min / month / org     | claims ~2× faster hardware; EU regions (Frankfurt, Amsterdam); no concurrency limit   |
| Celesto                | $0.00067 (`memory`)        | $5 one-time trial credit    | prepaid credit; ~20 concurrent runners by default; 2 h job limit; no stated EU region |

Rule of thumb: Blacksmith ≈ 1/3–2/3 of the github bill (depending on
how much faster jobs run), Celesto ≈ 1/9. Bigger runners for the slow
jobs (usually `test`) often cost about the same per job because the job
finishes faster.

## 3. Decide on data protection — explicitly

A runner is not just compute: **everything a job sees is on the
provider's machine in plain text** — github secrets and variables are
stored at github, but delivered decrypted to the runner for every job
that uses them, together with all env vars (catladder's `vars.public`
and `vars.secret` of that environment), the source code, the
`GITHUB_TOKEN`, OIDC tokens and cloud credentials (e.g. the GCP deploy
key). Log masking only hides secrets in the logs, not on the machine.

So choosing a provider is a data-protection decision for the customer
of the project, not a CI tweak. Check and record (e.g. in an ADR):

- where the runners run (region) and the provider's subprocessors —
  Blacksmith offers EU regions; Celesto lists US subprocessors (AWS,
  …) and no EU region as of November 2026
- whether the customer's contract / DPA allows that processor
- isolation (both use ephemeral microVMs per job) and the provider's
  security docs

To limit exposure, keep the environments whose secrets matter on
github's runners and run the rest cheaply:

```ts
runner: {
  default: { provider: "celesto" },
  environments: { prod: "ubuntu-latest", stage: "ubuntu-latest" },
  light: { provider: "celesto", size: "micro" },
  release: "ubuntu-latest", // release jobs: deploy key / npm credentials
},
```

Review, dev and test jobs then only see review/dev secrets.

## 4. Set up the provider

Both are GitHub Apps; installing the app alone does nothing until the
labels change.

**Blacksmith** — sign in at app.blacksmith.sh with the GitHub org, install
the GitHub App **on every repository that uses `blacksmith-*` labels**
(jobs of a repository without the app can be picked up by runners meant
for another one). Only organizations, not personal accounts.

**Celesto** — install the "Celesto CI" GitHub App, create/link a Celesto
workspace (you must be its admin), select the repositories, and top up
credit (Settings → Billing). Without credit jobs stay queued and the
"Celesto runner setup" check says so. Celesto's image is its own
Ubuntu 24.04, not github's — irrelevant for catladder jobs (they run
in their own container image), but relevant for hand-written workflows.

Then set `pipelines.github.runner`, run `catenv`, commit the regenerated
workflows and watch the first PR run. Roll back by removing the option
and regenerating.

## 5. Verify

- jobs are picked up (no "Waiting for a runner" for minutes)
- container jobs, service containers and docker builds work
- cache hits (`actions/cache` steps) — both providers serve the cache
  themselves, the first runs are cold
- compare the minutes of a week before and after (step 1)
